# Module 5 Firmware

## Overview

This module demonstrates timer, PWM, frequency measurement, external interrupt capture, and non-blocking software scheduling using an Arduino Uno with an ATmega328P running at 16 MHz.

The original module contained three separate programs:

1. PWM and duty-cycle control
2. Input frequency measurement
3. Software timer scheduler

They are combined into one firmware file:

```text
module5_firmware.ino
```

The firmware uses:

* Timer2 for PWM generation
* Timer1 for frequency measurement
* External interrupt on D2
* `millis()` for non-blocking software timers
* One LCD instance
* One `setup()`
* One `loop()`

There is no `delay()`.

---

## Hardware

* Arduino Uno
* ATmega328P
* 16x2 LCD
* Jumper wire from D3 to D2

# Tasks

## Task 1 – Timer2 PWM and Duty Cycle

### Objective

Generate a PWM signal on Arduino D3 using Timer2 and change its duty cycle periodically.

### PWM Pin

```text
D3
```

D3 is the OC2B output of Timer2.

### Timer2 Configuration

The firmware uses:

```text
Fast PWM
Prescaler = 64
TOP = 255
```

For a 16 MHz Arduino:

```text
PWM frequency = 16,000,000 / (64 × 256)

              = 976.56 Hz

              ≈ 977 Hz
```

Therefore the expected PWM frequency is approximately:

```text
977 Hz
```

### Duty Cycle

The duty cycle starts at:

```text
50%
```

It is updated every 1 second:

```text
50%
75%
100%
0%
25%
50%
...
```

The update is performed using `millis()`.

No blocking delay is used.

---

# Task 2 – Input Frequency Measurement

## Objective

Measure the frequency of the PWM signal generated by Task 1.

### Connections

Connect:

```text
D3 → D2
```

D3 generates the test signal.

D2 receives the signal through an external interrupt.

### Timer1

Timer1 is configured in normal mode with:

```text
Prescaler = 8
```

Arduino clock:

```text
16 MHz
```

Timer1 clock:

```text
16 MHz / 8 = 2 MHz
```

Therefore:

```text
1 Timer1 tick = 0.5 microsecond
```

The firmware measures the number of Timer1 ticks between two rising edges.

Frequency is calculated using:

```text
Frequency = 2,000,000 / periodTicks
```

### Expected Measurement

Because D3 is generating approximately 977 Hz PWM, D2 should measure approximately:

```text
977 Hz
```

The exact displayed value may vary slightly due to timer quantization and measurement timing.

The actual measured value from the hardware should be used as the final test result.

# Task 3 – Non-Blocking Software Scheduler

## Objective

Run multiple periodic tasks without using `delay()`.

Three independent software timers are implemented.

| Task   |  Interval |
| ------ | --------: |
| Task A |  1 second |
| Task B | 2 seconds |
| Task C | 5 seconds |

Each task has its own execution time and counter.

Example:

```text
A: 5
B: 2
C: 1
```

means:

* Task A executed 5 times
* Task B executed 2 times
* Task C executed 1 time

The counters continue increasing while PWM and frequency measurement are also running.

# Firmware Architecture

The complete firmware uses one Arduino file:

```text
module5_firmware.ino
```

Structure:

```text
module5_firmware.ino
│
├── Common includes
│
├── LCD
│
├── Pin definitions
│
├── Task 1
│   └── Timer2 PWM
│
├── Task 2
│   ├── Timer1
│   ├── D2 external interrupt
│   └── Frequency calculation
│
├── Task 3
│   ├── Task A
│   ├── Task B
│   └── Task C
│
├── LCD display states
│
├── setup()
│
└── loop()
```

There is only one:

```cpp
LiquidCrystal lcd(...);
```

one:

```cpp
setup();
```

and one:

```cpp
loop();
```

This avoids duplicate declarations and duplicate Arduino entry points.

# Non-Blocking Design

The firmware does not use:

```cpp
delay();
```

Periodic operations use:

```cpp
millis();
```

For example:

```cpp
if ((currentTime - lastTaskA) >= TASK_A_INTERVAL)
{
    lastTaskA += TASK_A_INTERVAL;
    countA++;
}
```

This allows the processor to continue running other firmware activities while waiting for the next scheduled event.

# Failure / Limitation Behavior

### No D3-to-D2 jumper

If D3 is not connected to D2:

```text
FREQ:Waiting
```

or no new valid frequency measurement will be available.

### Invalid period

If the measured period is zero, frequency calculation is skipped.

### PWM frequency

The PWM frequency is determined by the Timer2 hardware configuration and should not be described as exactly 500 Hz for this implementation.

### Timer resource usage

Timer2 is reserved for PWM.

Timer1 is reserved for frequency measurement.

The firmware does not configure either timer more than once.

# Summary

Module 5 demonstrates how multiple embedded firmware activities can operate together without blocking the processor.

```text
             MODULE 5
                 |
     +-----------+-----------+
     |           |           |
     v           v           v
   TIMER2      TIMER1      MILLIS()
    PWM       FREQUENCY    SCHEDULER
     |           |           |
     v           v           v
    D3          D2       A / B / C
     |           |
     +-----D3----+
        to D2
```

The final firmware uses one common architecture, one LCD instance, one setup function, one main loop, and no blocking delays.
